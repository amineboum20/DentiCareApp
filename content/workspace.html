Introduction

DentiCare est une application de gestion pour les cabinets dentaires. Elle couvre la gestion des patients, dossiers dentaires, actes, rendez-vous, factures et rapports. Chaque utilisateur (dentiste) voit uniquement ses propres données, isolées par Row Level Security côté Supabase.

RLS & Sécurité

Row Level Security est activé sur toutes les tables. Chaque politique vérifie auth.uid() = user_id. Cela garantit qu'un dentiste ne voit jamais les données d'un autre, même en cas de bug applicatif.

Les requêtes Supabase côté serveur (createClient() dans les Server Components) héritent du JWT de l'utilisateur connecté. Les routes API protégées redirigent vers /signin si non authentifié.

Authentification

DentiCare utilise Supabase Auth avec email + mot de passe. Le flux complet :

  1. L'utilisateur soumet le formulaire /signin
  2. Supabase valide les credentials et retourne un JWT
  3. Le cookie de session est stocké côté serveur (SSR-safe)
  4. Chaque Server Component appelle createClient() — le JWT est inclus automatiquement
  5. RLS filtre les données selon auth.uid()

Les pages du dashboard sont protégées par un middleware qui vérifie la session et redirige vers /[locale]/signin si absente.

Internationalisation

Le routing utilise next-intl v4 avec un segment dynamique [locale]. Les locales supportées sont fr (défaut) et ar. Les fichiers de traduction se trouvent dans messages/fr.json et messages/ar.json.

⚠️ Les chemins contenant [locale] nécessitent -LiteralPath en PowerShell pour éviter que les crochets soient interprétés comme des wildcards.

Le hook useTranslations('namespace') dans les Client Components et getTranslations('namespace') dans les Server Components donnent accès aux traductions.

Pattern composants

Chaque page suit le même pattern : un Server Component (page.tsx) qui fetch les données Supabase côté serveur, et un Client Component (XxxClient.tsx) qui reçoit les données en props et gère l'UI interactive (formulaires, modals, état local).

Ce pattern évite les waterfalls côté client et permet aux pages d'être SSR-first. Les modals s'ouvrent via le paramètre ?new=1 dans l'URL.

Gestion des patients

La liste des patients affiche uniquement les patients actifs (.is("archived_at", null)). On peut créer, éditer ou archiver un patient. La fiche patient utilise une disposition deux colonnes : informations personnelles à gauche, historique dossiers et factures à droite. Commit 89121ec — 2026-08-28.

Dossiers dentaires

Chaque patient possède un dossier dentaire unique regroupant ses antécédents, allergies et l'historique de tous ses actes. Le dossier est créé automatiquement à l'ajout du patient.

Actes dentaires

Un acte est lié à un dossier et référence le numéro de dent (notation ISO 3950). Types disponibles : détartrage, couronne, extraction, carie, autre. Le coût de l'acte alimente automatiquement la facture associée.

Rendez-vous

Le champ scheduled_at est un timestamptz (UTC). L'affichage et la saisie convertissent en heure locale. Types disponibles : consultation, soin, contrôle, urgence.

Factures

Chaque facture dispose d'un lien Voir individuel qui navigue vers la page de détail (/dashboard/factures/[id]). Statuts : en_attente → partiel → regle. Le statut annule est possible à tout moment. Commit 89121ec — 2026-08-28.

Rapports

La page rapports agrège : CA mensuel sur 6 mois, répartition des types d'actes, factures en attente, patients vus ce mois. Tout en inline CSS (pas de librairie de charts) pour éviter les dépendances externes.

Archivage (soft-delete)

Plutôt que de supprimer définitivement, les enregistrements sont archivés en settant archived_at = now(). Cela préserve l'intégrité des données médicales et financières. Les listes filtrent avec .is("archived_at", null).

Flux de déploiement

  1. Push GitHub — le développeur pousse sur main
  2. Vercel build — Next.js build automatique, type-check, lint
  3. Preview deploy — chaque PR génère une URL de preview unique
  4. Production deploy — merge sur main → déploiement prod en ~2 min
  5. Edge CDN — le bundle est distribué globalement via le réseau Vercel Edge

Sécurité

RLS Supabase : isolation totale par user_id — un opticien ne peut jamais voir les données d'un autre. JWT : tokens courts (1h) avec refresh automatique. Secrets : variables d'environnement Vercel (.env.local jamais commité). HTTPS : forcé partout via Vercel.

Application Mobile — Roadmap
