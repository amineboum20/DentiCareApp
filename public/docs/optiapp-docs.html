Technical Documentation

OptiApp is a multi-tenant SaaS application for independent opticians. Each optician manages their own clients, prescriptions, inventory, orders, and appointments — all isolated via Supabase Row Level Security.

Next.js 15 Supabase Vercel Live Auto-confirm ON

What was built

👤 Client management

Full CRUD — search, add, edit, delete with confirmation. Ordered by recency.

📋 Prescriptions

OD/OS optical values — sphere, cylinder, axis, addition, PD per eye. Linked to clients.

🕶️ Products

5 categories (frame, lens, contact_lens, accessory, other). Stock alerts at ≤ 3.

📦 Orders

Order items with optional product link or custom text. Inline status updates. Live total.

📅 Appointments

Grouped by day (Today / Tomorrow / date). Card-based with status colour bar.

📊 Reports

KPI cards + top items bar chart + low-stock alerts + revenue summary. All server-side.

Row-level security

All tables have RLS enabled. Every policy checks user_id = auth.uid(), so each optician sees only their own data — enforced at the database level, not in application code.

-- Pattern applied to clients, prescriptions, products, orders, appointments
CREATE POLICY "Users own their rows" ON clients
  FOR ALL USING (user_id = auth.uid())
  WITH CHECK (user_id = auth.uid());

order_items has no user_id column, so its policy uses a subquery:

CREATE POLICY "Users own their order items" ON order_items
  FOR ALL USING (
    EXISTS (SELECT 1 FROM orders
              WHERE orders.id = order_items.order_id
              AND   orders.user_id = auth.uid())
  );

Authentication

Supabase Auth with email + password. Sessions are stored in HTTP-only cookies managed by @supabase/ssr, making them available in both Server Components and middleware.

→

→

→

Note: mailer_autoconfirm is currently ON in Supabase — no email confirmation required. This was enabled because Resend's free plan only delivers to verified addresses. Re-enable confirmation once a custom sending domain is added.

Session check in layout

The dashboard layout (app/[locale]/dashboard/layout.tsx) is a server component that calls supabase.auth.getUser(). If no session exists, it redirects to /signin. This single guard protects all nested routes.

export default async function DashboardLayout({ children }) {
  const supabase = await createClient();
  const { data: { user } } = await supabase.auth.getUser();
  if (!user) redirect("/signin");
  // render Sidebar + children
}

User metadata

First name, last name, and shop name are stored in user.user_metadata at sign-up time via options.data. They're retrieved in the dashboard layout and passed to the Sidebar.

Internationalisation

Three locales: French (default), English, and Arabic (RTL). Routing is handled by next-intl — all pages live under app/[locale]/.

RTL support

Tailwind logical properties are used throughout instead of directional ones — ms-* instead of ml-*, ps-* instead of pl-*, start-0 instead of left-0. This means the layout automatically mirrors for Arabic without any extra CSS.

Sidebar active state

The Sidebar imports Link and usePathname from @/i18n/navigation — next-intl's wrappers that strip the locale prefix. This avoids a hydration mismatch where the server rendered /fr/dashboard/clients but the client saw /dashboard/clients.

Translation files

All UI strings live in messages/fr.json, en.json, and ar.json. Sections: nav, dashboard, clients, prescriptions, products, orders, appointments, reports, signIn, signUp.

Every dashboard page is split into two files:

This pattern keeps data fetching on the server (no loading spinners, no API routes needed) while keeping interactivity in the client where required.

Sidebar navigation

The sidebar is a client component (needs usePathname). It's rendered once in dashboard/layout.tsx and persists across all dashboard page navigations. Active state logic:

// Dashboard home: exact match only
const active = item.href === "/dashboard"
  ? pathname === "/dashboard"
  : pathname === item.href || pathname.startsWith(item.href + "/");

Pages

📊 Dashboard home /dashboard

Server component. Fetches 6 queries in parallel via Promise.all: total clients, orders this month, frames in stock, pending pickups, 5 recent orders (with client join), and 5 upcoming appointments. Shows KPI cards, recent orders table with status chips, and upcoming appointment list.

👤 Clients /dashboard/clients

Table with search (name/email/phone). Add/edit modal with required first + last name. Delete confirmation. Optimistic local state — no full page reload on mutations.

📋 Prescriptions /dashboard/prescriptions

Two-column OD/OS form (right eye / left eye). Values displayed with explicit +/− sign via formatSign(). Client dropdown populated server-side.

🕶️ Products /dashboard/products

Category filter tabs. Stock badge: red for 0, amber for ≤ 3, green otherwise. Form includes selling price, cost price, and SKU.

📦 Orders /dashboard/orders

Inline status <select> per row — status updates without opening the modal. Order items: product dropdown auto-fills description + price; free-text items also supported. On edit, items are fetched async, then on save: old items are deleted and reinserted.

📅 Appointments /dashboard/appointments

Calendar-style view grouped by day header (Today / Tomorrow / formatted date). Each card has a left colour bar by status, type icon, client name, and inline status dropdown.

📊 Reports /dashboard/reports

Pure server component. 4 KPI cards, top-5 items bar chart (aggregated from order_items), low-stock list, revenue summary (this month / last month / outstanding balance = total − deposits).

Mobile responsiveness

All pages are responsive across mobile, tablet, and desktop. The key pattern: Tailwind's logical properties (ms-*, ps-*, start-*) are used everywhere for automatic RTL support.

Dashboard sidebar

On mobile the sidebar is hidden by default. A fixed top bar (h-14, z-20) renders the logo and a hamburger button. Tapping it slides in the sidebar panel (translate-x-0) with a dark overlay; tapping outside or navigating closes it.

/* Sidebar.tsx — panel */
<div className=`fixed inset-y-0 start-0 z-40 w-64 sm:w-56 ...
  ${open ? "translate-x-0" : "-translate-x-full"} sm:translate-x-0`>

Landing page nav

The hamburger dropdown lives inside the <nav> element — which is sticky top-0 — so the dropdown remains visible wherever you are on the page when it opens.

Key decisions & fixes

🔒 Hydration mismatch — Sidebar active state

The server rendered /fr/dashboard/clients (with locale) but usePathname() from Next.js returned /dashboard/clients (no locale). Fixed by switching to Link and usePathname from @/i18n/navigation, which strips the locale from both sides.

⚙️ Signup freezing — missing Vercel env vars

The deployed app had no NEXT_PUBLIC_SUPABASE_URL or NEXT_PUBLIC_SUPABASE_ANON_KEY because .env.local is gitignored. The Supabase client threw silently and the signUp call never resolved. Fixed by adding both variables in Vercel project settings.

✉️ Signup freezing — Resend SMTP timeout

When a user signed up with any non-verified email, Resend's SMTP rejected the delivery, causing Supabase's signUp to block until SMTP timeout. Fixed by enabling mailer_autoconfirm: true. The signup flow now redirects to /dashboard when a session is returned immediately (data.session !== null).

📦 order_items RLS — no user_id column

order_items can't have a user_id = auth.uid() policy directly. Instead the policy uses an EXISTS subquery into orders, which does have user_id.

🌐 RTL — Tailwind logical properties

All spacing uses logical properties (ms-, me-, ps-, pe-, start-, end-) so the layout flips automatically when the Arabic locale sets dir="rtl" on the html element — no separate RTL stylesheet needed.

🗄️ Dummy data — user_id reassignment

Seed data was initially inserted for the first test account (yobepek170@kolsea.com). When a new account was created, all rows were reassigned by running an UPDATE … SET user_id = NEW_UID WHERE user_id = OLD_UID across all five tables via the Management API.

Environment variables

Required in both .env.local (local dev) and Vercel project settings (production).

VariableWhereNotes
NEXT_PUBLIC_SUPABASE_URLVercel + localProject URL from Supabase dashboard → Settings → API
NEXT_PUBLIC_SUPABASE_ANON_KEYVercel + localPublic anon key — safe to expose in client bundle
NEXT_PUBLIC_ prefix means the value is baked into the client-side JavaScript bundle at build time by Next.js. If missing at build time, the variable is undefined in the browser and the Supabase client throws silently.

The Supabase service role key and Resend API key are not needed at runtime — they were used only for one-off Management API calls during setup and should never be exposed to the browser.
